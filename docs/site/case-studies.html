Case Studies

Concrete platform decisions under real constraints.

These case studies describe the platform as an operating system, not as a design exercise. Each one focuses on a real problem, the constraints on a small single-VM host, the technical implementation choice that was made, and the operational outcome.

Last reviewed: November 2026 Format: problem, constraints, implementation, outcome

Case 01

From portfolio page to operable platform frontdoor

shellr.net Nginx Docker Compose

Problem: A portfolio landing page can look polished and still say very little about whether the operator understands delivery, failure handling, or runtime separation.

Constraints: One VM, limited disk, no orchestration layer, and no room for decorative infrastructure.

Implementation: The main site became the public frontdoor of a live platform with links to architecture, source, and public services.

Outcome: Reviewers can move from positioning to proof: architecture, deployment flow, and repository structure are accessible from the landing page.

Case 02

Isolating DMA as its own runtime surface

dma.shellr.net PHP MariaDB

Problem: Legacy PHP workloads become operational blind spots when they are embedded into a wider site without clear boundaries.

Constraints: Existing codebase, existing data model, and a need to preserve usefulness while improving runtime clarity.

Implementation: DMA was moved behind its own subdomain, container, cookie scope, database boundary, and health behavior instead of being treated as a path-level add-on. Its public endpoint now presents the architecture as a read-only showcase.

Outcome: The application is easier to route, test, monitor, and reason about, while still remaining usable as a live statistics tool.

Case 03

Observability without turning a single VM into a cluster

Prometheus Grafana Loki

Problem: Small hosts still need visibility, but full observability stacks quickly become disproportionate in memory, disk, and maintenance effort.

Constraints: 8 GB RAM, 40 GB disk, and a goal of staying understandable for one operator path.

Implementation: Prometheus, Grafana, Uptime Kuma, cAdvisor, Loki, and Grafana Alloy are kept on intentionally short retention and bounded storage instead of aiming for long-term analytics.

Outcome: The platform stays observable enough for incidents and review without pretending to be a multi-team observability platform.

Case 04

Reducing vulnerability-feed noise through asset relevance

ENISA EUVD SQLite Freshservice

Problem: Raw vulnerability feeds create review noise because new records do not directly identify the systems that are actually present in an environment.

Constraints: Upstream API availability, incomplete product naming, repeated records, and the need to avoid duplicate notifications.

Implementation: The current automation work maps ENISA EUVD records to an asset inventory, enriches relevant findings with CVSS, KEV, and EPSS context, and records revisions for repeatable review.

Outcome: The design moves vulnerability review from broad feed scanning toward a focused, asset-relevant daily workflow while keeping incomplete matches visible for manual validation.

Migration

Migration from a cloud VM to a homelab

Starting point. A cloud VM hosted the Compose stacks, MariaDB, reverse proxy, and observability. The goal was to move the services to a Docker VM on operator-owned Proxmox VE hardware while keeping their public URLs.

  1. Provision the destination, inventory the source, and test the offsite backup and restore path.
  2. Stage application files and required images. Transfer the files as a direct SSH tar stream with numeric ownership. Import MariaDB from a logical dump and verify the staged services locally.
  3. During the maintenance window, freeze source writes, take a final dump and file copy, and start the destination. Switch public ingress to Cloudflare Tunnel and verify DNS, HTTPS, and service responses.
  4. Keep the source and its previous routing configuration available for rollback until the destination is accepted. Confirm an encrypted offsite restore before retiring the source.

Cutover. The cutover interrupted public access for roughly 15–20 minutes. Direct edge checks confirmed both sites about 18 minutes after the old ingress stopped. Cached DNS on the operator’s client took longer to converge.

  • Bind-backed volumes: verify the actual backing paths, numeric ownership, and modes before starting containers. Restore MariaDB from a logical dump.
  • Loki permissions: a root-owned backing directory prevented Loki from writing. Matching the directory ownership to the container UID restored write access.
  • Transfer path: the PC relay was slow. A direct stream between the hosts removed that bottleneck.
  • IPv6 DNS: FRITZ!Box still advertised its own IPv6 resolvers after IPv4 DNS moved to Pi-hole. Verify both resolver lists on a client before removing temporary DNS entries.
