Docs / Monitoring

Internal metrics, logs and explicit state.

Prometheus and Grafana provide metrics, Alloy forwards logs to Loki, and the internal dashboard evaluates service, capacity, backup and image-scan evidence. Uptime Kuma remains during the comparison period.

State and freshness

Local and external backup success are separate signals with a 25-hour freshness limit. Missing evidence remains unknown. Guest filesystem utilisation is read with existing hypervisor audit access; unavailable measurements remain visible.

Default resource limits are 90 percent host RAM, 80 percent thinpool, and 85 percent hard-disk or guest-filesystem utilisation. Guest usage at 95 percent is critical. Most warnings need two consecutive failure or recovery samples. The API-outage limit is five minutes; stale-sampler checks remain time-dependent.

Monitoring-process and container-health status is identified separately from full application verification. Actual runtime images are compared with active Compose models and scanned at least weekly. Only aggregate findings and timestamps reach the dashboard.

Grafana authentication and headers

Grafana owns its nonce-based CSP. The proxy retains Basic Auth without duplicating Grafana headers. Deployment checks both the unauthenticated challenge and an authenticated origin response with fresh matching bootstrap nonces.

Grafana user passwords remain database state. The proxy password file remains private operator state; deploys and rollbacks do not regenerate it.

Accepted detection limit

No push, email or other alert delivery is configured, and there is no external notifying monitor. Host, power or Internet failure can also make the dashboard unavailable. Detection depends on the next operator check.
